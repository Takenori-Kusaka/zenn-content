## 3ステップ

### 1. テンプレートからリポジトリを作る

GitHub 上部の **Use this template** から新しいリポジトリを作ります。

### 2. `/process-init` を実行する

Claude Code でリポジトリを開き、次を実行します。

```
/process-init
```

5つの質問に答えます。**専門用語では聞きません。**

| # | 質問 |
| --- | --- |
| 1 | 開発に関わる人数は? |
| 2 | プロダクトはいまどの段階? |
| 3 | 品質への要求は? |
| 4 | 最悪の場合、何が起きる? |
| 5 | 開発の形態は? |

回答から、次が生成されます。

| 生成物 | 中身 |
| --- | --- |
| `PROCESS-PROFILE.md` | 人が読む構成書。標準からの差分と、その理由 |
| `process.config.json` | 機械が読む構成。CI とスキルが参照する |
| `.github/workflows/` | 有効なゲートだけが残る |
| `.github/rulesets/` | 規模に応じたブランチ保護 |

### 3. 作業スキルで回す

以降は、次のスキルを順に使うだけでプロセスに乗ります。

```
/spec-write       受入基準を書く
/task-breakdown   実装計画へ分解する
/implement        AI が実装する
/human-verify     人が差分を検証する
/gate-record      ゲート判定を記録する
/adr-write        設計判断を記録する
```

各スキルは構成ファイルを読み、あなたの構成で不要なゲートには触れません。

## 言語は問いません

CI が固定するのは**ゲート契約**だけです。

- 必須ステータスチェックの名前は `gate-g5`
- 出荷判定の証跡は `evidence/evidence.json` のキー構造

実際に走るテスト・静的解析・ライセンス検査のコマンドは、アダプタから差し込みます。`node` / `python` / `go` / `none` を同梱しています。

`none` を選んだ場合、コマンドを自分で書きます。**空のままにすると G-5 が失敗します。**検査を実施していない状態を通過した記録にしないためです。

## 生成される構成の例

1〜2名・PoC 段階の場合、こうなります。

| ゲート | 判定 |
| --- | --- |
| G-1 企画承認 | 簡略化して適用する |
| G-2 要件合意 | G-4 へ統合する |
| G-3 技術設計判断 | 適用する |
| G-4 機能仕様承認 | 適用する |
| G-5 自動検証 | 適用する |
| **G-6 独立レビュー** | **未達** |
| G-7 出荷判定 | 適用しない |
| G-8 リリース決裁 | 適用する |

10名以上・規制業・安全重要度が高い場合は、全ゲートが有効になり、承認2名・署名必須・カバレッジ下限の引き上げが入ります。

**どちらの場合も、判定の理由が各行に付きます。**スコアや成熟度のラベルは出しません。評価ではなく構成の導出だからです。

## 既存プロジェクトへ後から入れる場合

新規と違い、順序が重要です。おすすめの順番はこうです。

### 第1段階: 記録から始める

いきなりゲートを増やしません。まず記録の置き場を作ります。

- 判断記録(ADR)を `context/decisions/` へ書き始める
- ドメイン用語集を作る
- 技術負債台帳を作る(**記録だけ。返却計画はまだ作らない**)

これだけでも、AI へ渡せる文脈が増えます。

### 第2段階: G-5 を固める

自動検証を先に厚くします。人の判定を増やす前に、機械が判定できるものを機械へ寄せます。

- テストとカバレッジ
- 静的解析と脆弱性検査
- **秘匿情報の混入検査**(これは最優先)
- 曖昧語チェック

### 第3段階: G-6 を機械で強制する

ブランチ保護を入れます。`require_last_push_approval` を必ず有効にします。

### 第4段階: 受入基準の書き方を変える

ここは最も時間がかかります。曖昧語の禁止を CI へ入れて、少しずつ既存の仕様を書き直します。

### 第5段階: 外殻を対応づける

既存の稟議・出荷判定を、G-1 / G-7 / G-8 へ対応づけます。**新設ではなく対応づけです。**

## 最初にやらないほうがよいこと

| やらない | 理由 |
| --- | --- |
| 全ゲートを一度に有効にする | 判定者の帯域が飽和し、全部が形骸化する |
| AI 自律レベルを L2 以上から始める | 引き下げの検知手段が整っていない状態で上げない |
| 会議体を新設する | 既存の会議へ対応づけるほうが定着する |
| 閾値を最初から厳しくする | 実測がない状態の厳しい閾値は、例外運用を生む |
| 測定結果を評価に使う | 測定が忌避され、数値が作られるようになる |

---

## 閾値について

テンプレートが出す初期値(カバレッジ80%など)は、**実測に基づく値ではありません**。

自組織の値を、企画承認(G-1)の時点で決めて置き換えてください。テンプレートの値をそのまま使い続けると、「なぜその値なのか」を誰も説明できない状態になります。

同じ理由で、標準本文では根拠の弱い記述に識別子と見直し期限を付けて公開しています。どこが確からしくて、どこが暫定なのかを、読む側が判断できる状態を保つためです。

## この章のまとめ

- テンプレートから作り、`/process-init` で5つの質問に答える
- 言語は問わない。ゲート契約だけ固定し、コマンドはアダプタから差し込む
- 既存プロジェクトへは、記録 → G-5 → G-6 → 受入基準 → 外殻の順で入れる
- 全ゲートを一度に有効化しない。閾値は自組織の値へ置き換える
