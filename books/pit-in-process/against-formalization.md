「ルールを作っても、どうせ形骸化する」——これは正しい観察です。

レビューが印を押す操作になる。チェックリストが埋めるだけの欄になる。ゲートが通過儀礼になる。多くの人が見てきた光景だと思います。

この章の立場はこうです。**形骸化は意志の問題ではなく、条件の問題です。**だから条件のほうを塞ぎます。

---

## 形骸化が起きる条件

観察すると、いくつかのパターンに分かれます。

| パターン | 条件 |
| --- | --- |
| 逐行確認の縮退 | 確認すべき範囲が有界でない |
| 指示の空文化 | 守らなくても止まらない |
| 権限の一方向の拡大 | 引き上げは記録されるが、引き下げの契機がない |
| 検証の骨抜き | 検証そのものを緩める操作が、機能変更と同じ経路を通る |
| 測定の忌避 | 測定結果が個人の評価に転用される |

順に見ていきます。

---

## 1. 確認の範囲を有界にする

### 何が起きるか

「差分を全部読んで承認する」は、変更量が増えると必ず崩れます。時間の制約のもとで、逐行確認は**実質的な承認操作へ縮退します**。

しかも、この縮退は外から見えません。記録上は「レビュー済み」と残ります。**静かに嘘になる**のが最悪の性質です。

### 打ち手

読む量を増やす方向ではなく、**数え上げられるものだけを見る**方向へ設計を変えます。

| 順 | 見るもの | 範囲 |
| --- | --- | --- |
| 1 | 受入基準とテストの対応 | 受入基準の数だけ |
| 2 | 外部インタフェースの差分 | 変更されたインタフェースの数だけ |
| 3 | 差分の性質(追加/移動/複製) | 機械が分類したものだけ |
| 4 | 遮断の記録と機械判定のラベル | 件数は有界。0件なら見るものがない |
| 5 | 実装コード | **順1〜4で疑義が出た箇所に限定** |

順1〜4は全部数えられます。**「見終わった」と言える状態が定義できます。**順5だけが範囲の定まらない作業なので、最後に置き、対象を絞ります。

---

## 2. 指示ではなく強制層へ降ろす

### 何が起きるか

「〜してはならない」と規約に書いても、守られるとは限りません。とくに AI エージェントに対しては、**指示ファイルの遵守は保証されません**。

### 打ち手

規約を2層に分けます。

| 層 | 置くもの | 例 |
| --- | --- | --- |
| 誘導層(指示ファイル) | 判断の指針、範囲外へ出るときの確認要求 | CLAUDE.md、レビュー観点 |
| **強制層**(実行環境の設定) | 書き込み範囲、ネットワーク、コマンドの許可リスト | 権限設定、ブランチ保護、CI |

**強制層に置けない項目は、遮断できたものとして数えません。**

具体的には、次を既定で拒否します。

| 対象 | 既定 | 許可する範囲の決め方 |
| --- | --- | --- |
| 書き込み | 拒否 | 実装計画のタスクが対象とするパス |
| 読み取り | リポジトリ内は許可 | 秘匿情報を含む経路を除外する |
| ネットワーク | 拒否 | 依存関係の取得先など必要な宛先のみ |
| コマンド実行 | 許可リスト | 実行を許すコマンドを列挙する |

そして重要な要求が1つあります。

:::message alert
**設定の変更が、エージェント自身の操作では行えないこと。**
これを満たさない基盤では、遮断は成立しません。範囲を広げる操作が実行の一部として行えてしまうためです。
:::

拒否された操作は記録に残します。拒否の発生そのものが、タスクの範囲設定が実態と合っていない兆候だからです。

ただし限界も明記します。**遮断が0件でも、想定外の操作がなかったことにはなりません。**「拒否が0件だから安全である」とは記録しません。

---

## 3. 引き上げは判定、引き下げは自動

### 何が起きるか

権限や自律レベルは、上がる方向にだけ動きがちです。上げるときは「うまくいっている」という根拠がありますが、**下げるときの契機は誰も作りません**。

監督の劣化は静かに進み、申告されません。

### 打ち手

非対称を意図的に設けます。

- **引き上げ**: 条件をすべて満たしたときに申請し、判定を受ける
- **引き下げ**: 検知した時点で自動的に発火する

引き下げの検知条件で、最も特徴的なのはこれです。

| 検知する状態 | 措置 |
| --- | --- |
| **独立レビューの差し戻し率が0%のまま推移した** | **形骸化の疑いとして引き下げる** |

差し戻しが一度も出ないレビューは、うまくいっているのではなく**見ていない**可能性があります。上下どちらの逸脱も異常として扱います。

同じ非対称を、他の場所にも効かせています。

- 欠陥注入の演習は、障害対応中やリリース凍結期間に**自動で停止**する。停止の解除は人の操作による
- プロセス構成を厳しくする変更は自由。**緩める変更は記録を要する**

## 4. 検証を緩める操作を分離する

### 何が起きるか

テストが落ちたとき、テストのほうを直せば通ります。カバレッジ基準を下げれば通ります。静的解析の重大度設定を変えれば通ります。

**これらは実装の完了ではなく、検証の放棄です。**そして差分の見た目では、正常な変更と区別が付きにくい。意識して探さなければ通過します。

### 打ち手

3段構えにします。

**1. 機械判定で止める**

カバレッジ閾値・静的解析の重大度・検査の除外設定の変更は、機能の変更とは**別の変更単位に分離**させます。同じ PR に混ぜたら CI を通しません。これらの変更は、以後のすべての通過を無効化するからです。

**2. ラベルを付ける**

テストの削除、アサーションの削除、`skip` の付与は、正当な場合(仕様変更に伴う削除)と区別が付きません。だから**合否条件にはせず、ラベルを付けて独立レビューの必須確認事項にします**。

区別できない検査を合否条件に置くと、正当な変更まで止まり、検査の除外が常態化します。

**3. 自己修正ループの書き込み範囲から外す**

自動検証の失敗を AI に渡して修正させるループでは、**書き込み範囲にテストを含めません**。渡された失敗を、テスト側の変更で解消する経路が残るためです。

これは指示ではなく設定で行います。テストの修正を要すると判明したら、ループを終了して人が受入基準へ戻ります。ループの内側で続けません。

## 5. 測定の対象を工程にする

### 何が起きるか

プロセスを測ろうとすると、測定結果が個人の評価に転用されます。すると人は測定を避けるか、測定される数値を作りにいきます。

「レビュー指摘件数」を評価に使えば、指摘しやすい箇所だけを指摘する方向に最適化されます。実務で問題になる欠陥の多くは**記述の欠落**であり、探しにくい側が残ります。

### 打ち手

測定の対象を**工程**に限ります。

- 集計はチーム単位・工程単位に限る。**個人単位の検出率を算出しない**
- 結果を人事評価および処遇の材料にしない
- 検出に対する報奨・表彰・順位付けを行わない
- 記録に、検出者・見逃した者の個人識別子を含めない

そして、これを**事前に周知します**。「試されている」という受け取りは、位置づけの言い換えでは消えません。測定の対象が工程であることを明示するしかありません。

---

## 6. 判定の場を増やさない

最後に、全体を貫く原則を1つ。

**判定の場を増やしても、質は上がりません。**

承認者を2人にすれば、それぞれが「もう1人が見ているだろう」と考えます。ゲートを増やせば、各ゲートの重みが下がります。

質を上げる方法は1つです。**1回の判定対象を小さくすること。**

| やること | やらないこと |
| --- | --- |
| 1タスク = 1レビュー単位に収める | 承認者を増やす |
| 変更行数・ファイル数に上限を置く | ゲートを追加する |
| レビュアの同時保有数に上限を置く | チェック項目を増やす |

同時保有数の上限に達したら、**受け入れを止めます**。判定を省略して受け入れることをしません。上限に繰り返し到達する場合、原因は受け入れ速度ではなく、その手前の検証の水準にあります。

## この章のまとめ

| 防ぐもの | 手段 |
| --- | --- |
| 逐行確認の縮退 | 確認の範囲を有界にする |
| 指示の空文化 | 強制層(実行環境の設定)へ降ろす |
| 権限の一方向の拡大 | 引き上げは判定、引き下げは自動 |
| 検証の骨抜き | 基準値の変更を分離し、削除にはラベルを付ける |
| 測定の忌避 | 測定の対象を工程に限り、個人を評価しない |
| 判定の希薄化 | 判定の場を増やさず、1回の対象を小さくする |
