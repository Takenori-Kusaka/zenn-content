生成AIを開発へ組み込むとき、実際の問題は AI の賢さではありません。**組織側の前提**です。

現状のプロセスと、AI 前提のプロセスを突き合わせると、埋めるべきギャップが5つ出てきます。

:::message
**技術のギャップは時間が解きます。組織のギャップは待っても埋まりません。**「決定権が職位で決まる」「稟議が責任を分散する」「暗黙知が明文化されない」は、モデルが賢くなっても変わりません。
:::

## G1 明文化の壁

### 何が起きるか

AI に渡す文脈が足りず、生成物が的を外します。しかし本当の問題はその先にあります。

**暗黙知を言葉にする作業は、書いた本人にとっては自明です。**だから書く動機が生まれません。「そんなの当たり前でしょう」と思っている知識ほど、AI には渡っていません。

さらに、チケットごとに前提を書き直す運用にすると、書く量が線形に増えて続きません。

### 打ち手

**一度書いて、繰り返し使う**構造にします。文脈を3層に分けます。

| 層 | 内容 | 更新の頻度 |
| --- | --- | --- |
| 恒久層 | ドメイン用語、設計標準、判断記録 | 低い |
| 案件層 | この案件の前提、決まっていないこと | 案件ごと |
| 実行時 | このタスクで参照する範囲 | 毎回 |

恒久層はリポジトリに置き、変更履歴で追跡します。**責任者を割り当てます**(誰も持たない文脈ファイルは陳腐化します)。

そして、書き戻しを**作業として工程に組み込みます**。「あとでまとめて」は行われません。

## G2 責任主体の欠落

### 何が起きるか

AI が生成した成果物に、責任を持つ人のいない状態が生まれます。

- 「AI が書いたので分かりません」
- 「レビューは通っていますが、中身は見ていません」
- 承認欄に印はあるが、誰が結果を引き受けるのかが不明

取締役会や監査部門が最も嫌う状態です。そして、稟議による多数承認の文化は、この状態を**作りやすい**方向に働きます。

### 打ち手

責任分担を RACI で表し、**A(結果責任)を各成果物に1人だけ**割り当てます。

| 原則 | 内容 |
| --- | --- |
| A は1人 | どの成果物にも結果責任者は1人。2人以上にしない |
| **AI は A になれない** | AI はどこまでも R(実行)。結果責任は必ず人間に紐づく |
| 委譲しても A は残る | 判定を委譲しても、結果責任は元の人に残る |

体制図(誰がどの役割か、どこまで兼務するか)は**規模によらず必須**です。人数が少ないほど兼務が増え、誰の決定なのかが曖昧になるためです。会議体は減らせますが、**決定の権限と境界の記述は減らせません**。

## G3 職位ゲートと専門性の乖離

### 何が起きるか

技術判断を、技術の分からない職位者が決裁します。

決裁者は中身を判断できないので、差し戻す根拠を持てません。結果として**素通しになる**か、あるいは判断できないことへの不安から**説明を要求し続けて滞留する**か、どちらかに振れます。

AI 生成コードでは、この問題が拡大します。量が増え、専門性の要求も上がるためです。

### 打ち手

**技術判断ゲートと事業決裁ゲートを分離します。**

| ゲート | 判定するもの | 誰が |
| --- | --- | --- |
| G-3 技術設計判断 | 設計の可逆性、非機能の充足見込み、代替案との比較 | 技術判断者 |
| G-1 / G-8 事業決裁 | 投資判断、リリースの是非 | 事業決裁者 |

技術判断者は**職位ではなく技術力量で任命**します。事業決裁者は技術判断に関与しません。

技術判断の記録(ADR)には、事業への影響を**観測できる事象**で書かせます。金額での定量化は義務にしません。書く場合は「算定の根拠」「過去の類似案件」「その額にならない条件」の3点を併記させます。

## G4 ロールの曖昧さ・兼務

### 何が起きるか

**作成者が自分の成果物をレビューする構造**ができます。

小規模なチームでは自然にこうなります。「実質的に自分しか分からないので、自分が見るしかない」。そして、これは独立レビューの意味を消します。

作成時に抱えた思い込みは、同じ人が見ても見つかりません。

### 打ち手

兼務の可否を明示的に定めます。可のものと不可のものを列挙します。

| 組み合わせ | 可否 |
| --- | --- |
| 価値責任者 × 文脈オーナー | 可 |
| 技術判断者 × 開発者 | 可 |
| 価値責任者 × 技術判断者 | 5名未満のみ可 |
| **作成を指示した本人 × 独立レビュア(同一成果物)** | **不可** |
| **開発ライン × 出荷判定者(同一案件)** | **不可** |

不可の2つは、**ブランチ保護の設定で機械的に強制します**。規約に書くだけにしません。

最小体制は3名です(作成指示者・レビュア・判定者の分離の下限)。3名未満では、独立レビューを外部に求めます。それも難しい場合の扱いは[第8章](solo-developer)で扱います。

## G5 承認滞留

### 何が起きるか

**AI が3時間で書き、承認に3週間かかる。**

これは AI 導入の効果を最も分かりやすく打ち消します。そして、滞留が続くと現場は迂回路を探します。「小さい変更だから承認は後で」「今回は急ぐので飛ばす」——この迂回が常態化した時点で、プロセスは書類の上だけのものになります。

### 打ち手

3つを組み合わせます。

**1. 判定を単独にする**

合議体を判定の場にしません。事前の非同期コメント期間は置きますが、判定は1人が行います。

**2. 期限を置き、超過を自動承認にしない**

| ゲート | 期限の目安 |
| --- | --- |
| G-2 要件合意 / G-3 技術設計判断 | 48時間 |
| G-4 機能仕様承認 | 24時間 |
| G-6 独立レビュー | 応答1営業日 / 判定2営業日 |
| G-7 出荷判定 | 3営業日 |

超過した場合は**エスカレーションします**。自動承認にすると、期限が「待てば通る時間」になります。

**3. 1回の判定対象を小さくする**

1タスク = 1レビュー単位。変更行数の目安100行、上限400行。変更ファイル数の目安10、上限15。

**判断の質を保つ最も確実な方法は、1回の判断対象を小さくすることです。**承認者の人数を増やしても、この効果は代替できません。

さらに、レビュアあたりの**同時保有数に上限**を置きます。上限に達したら受け入れを止めます。**判定を省略して受け入れることをしません。**

## もう1つの発見: 事業継続性の責任が社内に戻る

5つのギャップとは別に、構造的な変化があります。

従来、外注に出した部分は「社外に理解者がいる」状態でした。AI へ委譲した部分では、**理解している人間が社内・社外のどこにもいない**状態が生まれます。

これは、外注に預けていた事業継続性リスクが、**AI 委譲では社内の理解維持能力しだいになる**ことを意味します。

だから「何を人が理解し続けるか」の線引きが、プロセス設計の要になります。

- コア機能を宣言する(人が理解を維持し続ける対象)
- コア機能の理解保持者の人数を数える
- 理解保持者が1名になったら、その機能の AI 自律レベルを引き下げる

## ギャップと打ち手の対応

| ギャップ | 打ち手 |
| --- | --- |
| G1 明文化の壁 | 恒久層に一度書き、書き戻しを工程に組み込む |
| G2 責任主体の欠落 | A は1人。AI は A になれない。体制図を必須にする |
| G3 職位ゲートと専門性の乖離 | 技術判断ゲートと事業決裁ゲートを分離する |
| G4 ロールの曖昧さ・兼務 | 兼務の可否を明示し、不可のものは設定で強制する |
| G5 承認滞留 | 単独判定 + 期限 + 判定対象の縮小 + 同時保有数の上限 |
